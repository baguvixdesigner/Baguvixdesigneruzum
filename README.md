# Uzum × Taobao/1688 Trend Bot

Telegram-бот поиска товарных ниш: пересечение трендов на Taobao/1688 со свободными
(ещё не занятыми) нишами на Uzum Market. Полное ТЗ — см. документ, приложенный к задаче.

Стек: TypeScript, Node.js, [Telegraf](https://telegraf.js.org/), Prisma + PostgreSQL.

## 1. Архитектура

```
prisma/schema.prisma     — все модели из ТЗ (Category, ProductSnapshot, TelegramUser, кошелёк и т.д.)
src/config/env.ts        — загрузка и валидация переменных окружения
src/db/prisma.ts         — синглтон Prisma Client
src/services/
  exchangeRate.ts         — курс CNY→UZS с фида ЦБ РУз, кэш (CACHE_TTL_HOURS)
  apifyChina.ts             — сбор с Taobao/1688 через Apify-акторы (см. раздел 5)
  uzum.ts                   — поиск совпадений через graphql.uzum.uz
  uzumAuth.ts                — автоматическое получение Bearer-токена Uzum
  translate.ts               — перевод названий товаров на русский
  pipeline.ts                 — полный пайплайн сбора по категории (раздел 5 ТЗ)
  search.ts                    — выдача закэшированных товаров пользователю постранично
  wallet.ts                     — баланс, списания, заявки на пополнение
  categories.ts                  — список категорий v1 (раздел 3 ТЗ)
src/i18n/                  — словари фраз RU/UZ + t() хелпер
src/bot/                    — Telegraf-бот: клавиатуры, сессии, хендлеры (флоу раздела 6 ТЗ)
scripts/seed.ts              — засевает категории v1 в БД
```

## 2. Локальный запуск

```bash
npm install
cp .env.example .env        # заполнить BOT_TOKEN, ADMIN_TELEGRAM_ID, APIFY_TOKEN и т.д.
docker compose up -d        # поднимает PostgreSQL локально
npm run prisma:migrate      # создаёт таблицы
npm run seed                # засевает категории v1
npm run dev                 # запускает бота (tsx watch)
```

Для продакшн-сборки: `npm run build && npm run start` (перед этим `npm run prisma:deploy`
вместо `prisma:migrate`).

## 3. Переменные окружения

См. `.env.example` — там же комментарии по каждой. Ключевые:

- `BOT_TOKEN` — токен бота от @BotFather.
- `ADMIN_TELEGRAM_ID` — telegram_id Карима (получает заявки на пополнение и предложенные категории, единственный, кому доступны админ-действия внутри бота).
- `APIFY_TOKEN` — единый токен Apify-аккаунта: используется и для сбора с Taobao/1688 (`apifyChina.ts`), и как резерв для Uzum (`APIFY_UZUM_ACTOR_ID`).
- `TOPUP_CARD_NUMBER` / `TOPUP_CARD_HOLDER` — реквизиты, которые бот показывает при пополнении.
- `QUERY_PRICE_SUM` (14 900), `MIN_TOPUP_SUM` (50 000), `CACHE_TTL_HOURS` (24) — бизнес-константы из ТЗ, вынесены в конфиг, чтобы менять без правки кода.

## 5. Что сознательно оставлено как гипотеза / требует проверки перед продакшеном

1. **Источник данных Taobao/1688 — Oxylabs отклонён, переключено на Apify.** В исходном
   ТЗ предполагался единый платный Oxylabs E-Commerce Scraper API. Прогнали бесплатный
   пробный доступ (см. `scripts/prototype-oxylabs.ts`) и выяснили:
   - В официальном списке "именных" e-commerce источников Oxylabs с авто-парсингом **нет
     ни Taobao, ни 1688** — только generic `source: "universal"` (сырой HTML без структуры,
     `parse: true` для них явно отклоняется ошибкой "allowed only with parser_type...").
   - Даже сырой HTML для Taobao ненадёжен: страница — SPA, товары подгружаются отдельным
     асинхронным JS-запросом уже после начального рендера. С `render: "html"` и явным
     `browser_instructions: [{type: "wait", wait_time_s: 6}]` получили полную страницу
     (400КБ), но без единого признака данных товаров (0 совпадений `¥`, 0 ссылок на товар,
     0 price-классов) — то есть даже управляемый рендер с ожиданием не гарантирует, что
     нужный JS-запрос успеет отработать.
   - Вместо реверс-инжиниринга защиты Taobao с нуля — переключились на специализированные
     готовые акторы **Apify** (уже используется в проекте как резерв для Uzum, тот же
     токен `APIFY_TOKEN` подходит): `zen-studio/taobao-search-scraper` (поиск по ключевому
     слову, подтверждённый параметр `keyword`) и `zen-studio/1688-wholesale-scraper`
     (1688 — оптовая B2B-площадка, что хорошо ложится на пометку «опт» в разделе 2 ТЗ).
     Реализовано в `src/services/apifyChina.ts` — тот же интерфейс `searchChinaSource`,
     что был у `oxylabs.ts`, так что `pipeline.ts` изменился минимально.
   - **Оба актора проверены живыми прогонами** (`scripts/prototype-apify-china.ts`) —
     параметры `{keyword, maxItems}` подтверждены для обоих (у Taobao `maxItems` должен
     быть ≥ 10, иначе актор отклоняет вход). Реальные поля ответа заметно отличаются
     между сайтами — `apifyChina.ts` разбирает их раздельно (`parseTaobaoItem` /
     `parse1688Item`):
     - Taobao: `itemId`/`title`/`url`/`mainPictureUrl`; `price` — строка ("139.00");
       `sales`/`totalSold` на практике часто 0 даже на обогащённом товаре — реальный
       сигнал продаж лежит в `salesSignal` как человекочитаемая строка с иероглифом-
       множителем (например `"1万+"` = 10 000+), для чего добавлен `parseChineseCount()`.
     - 1688: `offerId`/`title`/`detailUrl`/`images[]`; `price` — объект `{min, max,
       currency}` (диапазон оптовых цен); `saledCount`/`orderCount`/`recentSoldCount` —
       уже готовые числа, парсинг не нужен. Заодно приходит масса B2B-контекста
       (поставщик, MOQ, рейтинг фабрики) — пока не используется, но при желании можно
       расширить `ChinaCandidate` под неё.
   - Экономика поменялась: вместо фиксированной подписки Oxylabs ($49/мес) —
     Apify тарифицируется по числу результатов (ориентир по прайсу Taobao-актора:
     ~$6 за 1000 базовых результатов). Нужно прикинуть реальный расход при разработке
     (сколько категорий × сколько ключевых слов × TTL 24ч) и сверить с ценой запроса
     пользователя (14 900 сум).
2. **Схема GraphQL Uzum — полностью решено и подтверждено живыми прогонами.**
   Официальной документации не существует (раздел 5.1 ТЗ). Итог расследования:
   - Домены `graphql.umarket.uz` / `api.umarket.uz` из исходного ТЗ **больше не резолвятся**
     (проверено DNS с реального VDS) — устарели. Актуальный бренд-домен: **uzum.uz**.
   - `graphql.uzum.uz` резолвится, но без заголовков отвечает 401 с пустым телом — это
     отказ шлюза (Apollo Federation — видно по subrequest-ошибкам от отдельных сервисов
     вроде `ad-market`), не ошибка GraphQL-сервера.
   - Интроспекция схемы у них **не отключена** — этим воспользовались вместо угадывания
     вслепую: нашли реальный запрос `makeSearch(query: MakeSearchQueryInput!):
     MakeSearchResult`, обязательные поля (`showAdultContent`, `filters`, `sort`,
     `pagination`), структуру карточки товара (`items[].catalogCard` — union
     `ProductCard | SkuCard | SkuGroupCard`) и, главное, поле **`ordersQuantity`** прямо
     на карточке — это и есть число заказов из раздела 4 ТЗ (`uzumOrdersSum`).
   - **Авторизация — тоже решена и автоматизирована.** GraphQL требует
     `Authorization: Bearer <JWT>` — анонимный токен от сервиса "Uzum ID", живёт ~3 часа.
     Через DevTools нашли, как его получает сам сайт:
     1. `GET https://uzum.uz/` → `307` → `Set-Cookie: _yasc=...` (кука привязки к серверу
        балансировщика Yandex Cloud — `server: ycalb`, **не HttpOnly**, ставится чистым
        HTTP-редиректом без JS/капчи).
     2. `POST https://id.uzum.uz/api/auth/token` с этой кукой, пустое тело →
        `Set-Cookie: access_token=<JWT>` (HttpOnly — недоступно JS в браузере, но обычный
        HTTP-клиент читает `Set-Cookie` напрямую).
     Это воспроизведено в `src/services/uzumAuth.ts` (`getUzumBearerToken()`) — токен
     получается и кэшируется автоматически (обновляется за 5 минут до истечения `exp` из
     самого JWT), никакого ручного копирования из DevTools для продакшена больше не нужно.
     `UZUM_BEARER_TOKEN` в `.env` остался как ручной оверрайд для отладки.
   - **Живой прогон подтвердил всё целиком, включая авто-получение токена**: `HTTP 200`,
     `total: 7449` по «женское платье», реальные цены в сумах, фото, `ordersQuantity`.
   - **`ordersQuantity` отдельно перепроверен и подтверждён рабочим.** При сортировке по
     релевантности (её и использует пайплайн) у топовых по совпадению товаров он часто
     0 — это не баг, просто у этих конкретных товаров мало недавних заказов. Пересортировка
     по `BY_ORDERS_NUMBER_DESC` сразу показала реальные ненулевые значения (20-60), заметно
     меньшие, чем накопленное число отзывов — похоже, это скользящее окно (недавняя
     активность продаж), а не общее число за всё время. Для сигнала «ниша ещё свободна» это
     даже уместнее общего исторического объёма.
   - Если в будущем это упрётся в анти-бот защиту (сейчас её нет) — пункт 8 раздела ТЗ
     уже предусмотрел резерв: платный **Apify Uzum Scraper** (переключение через
     `APIFY_TOKEN` + `APIFY_UZUM_ACTOR_ID`, код уже готов в `searchUzumViaApify`).
3. **Пороги `noveltyLabel`.** В `pipeline.ts` (`NOVELTY_THRESHOLDS`) — заглушка
   (🟢 ≤ 50 заказов, 🟡 ≤ 500, 🔴 выше). Согласно ТЗ, точные пороги подбираются на реальных
   данных при разработке — поменять одну константу после первых прогонов.
4. **Китайские поисковые запросы** в `src/services/categories.ts` (`chinaSearchTerms`) —
   первая версия ключевых слов на китайском для каждой подкатегории. Стоит свериться с
   реальной выдачей Apify-акторов и при необходимости расширить/уточнить список на категорию.
5. **Перевод названий.** По умолчанию используется неофициальный Google Translate endpoint
   без ключа (`TRANSLATE_PROVIDER=google-unofficial`) — у него неявные лимиты. Для продакшн-
   нагрузки переключить на `TRANSLATE_PROVIDER=yandex` с `YANDEX_TRANSLATE_API_KEY`.
6. **Сессии бота** сейчас в памяти процесса (`telegraf` in-memory session store) — подходит
   для одного процесса на VDS. При масштабировании на несколько инстансов — заменить на
   Redis-backed session store.

## 6. Деплой на VDS

1. Склонировать репозиторий на сервер, `npm ci`, `npm run build`.
2. Поднять PostgreSQL (см. `docker-compose.yml` как образец, либо использовать существующий на VDS, как в других проектах — Terracotta/шаблон Instagram-магазинов).
3. Заполнить `.env` на сервере (реальный `BOT_TOKEN`, `APIFY_TOKEN`, реквизиты карты).
4. `npm run prisma:deploy && npm run seed`.
5. Запустить `node dist/index.js` под процесс-менеджером (pm2/systemd), чтобы бот
   переживал рестарты сервера.
6. Протестировать на 2-3 категориях перед полным включением остальных (`Category.active`
   можно переключать прямо через админ-функции бота, когда они понадобятся, или напрямую в БД
   для первого теста).
